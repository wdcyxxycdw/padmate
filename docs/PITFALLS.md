# Verified technical facts (pitfalls)

[中文](PITFALLS.zh-CN.md)

Ten sections, by area of the code. Before you change a part of the code, read its section.

## SDL and controllers

### Basic behavior and hints
- **SDL hints**: before `SDL_Init`, `input.Open` sets `SDL_JOYSTICK_ALLOW_BACKGROUND_EVENTS=1`, `SDL_NO_SIGNAL_HANDLERS=1` (otherwise SDL takes Ctrl+C) and `SDL_JOYSTICK_HIDAPI_COMBINE_JOY_CONS=0`, then the preset and `--hint`. A hint of the same name in the environment wins. `SDL_Quit` resets the hints, so each Open sets them again.
- **SDL behavior**: SDL sends events only for open gamepads, so a gamepad is opened on GAMEPAD_ADDED. The first value of each axis is sent twice. For a virtual gamepad, `VirtualJoystickDesc.Version` is filled in by hand as 136, and `SDL_UpdateJoysticks` must be called after changing its state. On detach, SDL first lifts held buttons and centers the axes, then sends removed; padmate still has to ReleaseAll. Device ids are not reused within a process; a reconnect is recognized by DeviceKey (IN-09). The release of the guide button is delayed to 250 ms after the press, and presses in between are dropped.

### Device info and identity
- **What DeviceKey rests on**: a virtual gamepad has an empty serial and path; its GUID is `ff00`, the CRC-16/ARC of the name, the first 9 bytes of the name, then `00 76 01`. Virtual gamepads of the same name can only be told apart by #N; for two whose names share their first 9 bytes, SDL reports the second under the first one's name, so tests make the first 9 bytes differ. XInput's path is the slot, and DeviceKey does not use it.

### Recovering from disconnects and lost events (DMN-12)
- **Rescan on wake**: `Reenumerate(ctx)` publishes the full state as a `DeviceState` that cannot be dropped; wait for its internal fence to pass before `Supervisor.Sync`. The router treats the snapshot as a Resync, not as a new press. While a receiver is still dormant, it must not be brought back from cached state.

### 2.4 GHz receivers and the Switch protocol (IN-30)
When the Nova 2 Lite receiver is plugged in, it is first a vendor HID 3537:2106 (SDL does not list it); about 0.6 s later the controller connects and it becomes 3537:1098. In Switch mode (057e:2009, hidapi switchpro) it is enumerated as long as the receiver is plugged in, and SDL reports no removal when the controller turns off; do not diagnose it with `hidapi-off`.

- **2.4 GHz receivers**: over USB, the ConnectionState of a HIDAPI device is always WIRED, so it cannot tell that the controller turned off. A non-Bluetooth Switch controller that is silent for 100 ms only gets ForceUSB sent again; it is not disconnected, and the button state stays as it was before it turned off. Reports produce events only on changes, so neither the absence of events nor the absence of held controls proves that the controller is still there.
- Closing the gamepad puts a USB Switch device back into simple mode, after which it no longer reports properly: do not close it after a synthesized disconnect.
- The resend is a synchronous write on T-input; each `hid_write` waits up to 1 s and tries 5 times (not tested), so "T-input stalled" cannot always be taken for sleep: the watchdog's grace is given once per silent stretch. The heartbeat reads HID reports itself (`DeviceInfo.Path` goes to `SDL_hid_open_path`, called only on connect; `SDL_hid_read_timeout(…, 0)` does not wait): in the full report 0x30, bytes 3–11 are the buttons and sticks, and only when they are unchanged while the timer in byte 1 changes does it prove that the device keeps reporting.

### Feedback effects
- SDL's `Rumble` does not queue: a call simply overwrites the one before. The mixer of `internal/haptic` schedules step by step on T-input, and sends a stop effect on a new program, a lost link and exit. `SetFeedback` carries a target `DeviceID`; with several controllers, layer state must not be broadcast; only 0 broadcasts.
- **`--dry-run` drives physical controllers too**: layer switches and pause make a real controller rumble and light up. Tests use only fake sources (`fakeSource` and the like) or virtual gamepads; never send `SetFeedback` to `Device` 0 (a broadcast to every one) in a test that may open a real controller.
- **Effect channels** (read from the source, not on real hardware):
  - LED: `SDL_SetJoystickLED` returns success at once when the color has not changed and its 5 s window has not passed, and it records the color after calling the driver whether or not that worked; so after a failed write, the same color within the window counts as a repeat. The LED cool-down is 7 s (`LEDCooldown`).
  - Rumble: when the strength equals the current one, `SDL_RumbleJoystick` does not call the driver, so between adjacent "on" steps, and when preempting, `Rumble(0,0,0)` is sent first. A duration of 0 with a non-zero strength rumbles forever; each step is limited to 1–5000 ms. Switch HIDAPI merges rumble writes into one every 30 ms and does not support trigger rumble; XInput has Rumble only, with no trigger rumble, LED or player number. Calls must follow the capabilities.
  - **Player numbers** are one table for the whole SDL process: give B the number n, and A, which held n, is moved. So before cycling, ask the whole table with `Effector.PlayerIndexTaken(n)` and use only free numbers; a controller without player lights must not touch the numbers. Writing a number for a controller SDL has removed stores a dead instance id in the table that nobody clears; for removed ones use `Mixer.Forget` and do not call the `Effector`.

### Battery readings (IN-12)
Written from the source (except the receiver entry). In go-sdl3, `SDL_POWERSTATE_ERROR` is the `uint32` 4294967295; do not take it for -1. The battery is a `DevicePower` event; do not add it to `DeviceInfo` (which must stay comparable, and is the format of traces). `low` in the state means "the warning went out and has not re-armed", not "the battery is low"; a new episode is recognized by the `episode` number.

- **The battery of a controller behind a 2.4 GHz receiver is a fake full charge** (tested on the Nova 2 Lite): CHARGING 100 % in Xbox mode, CHARGED 100 % in Switch/PS4 mode. The low-battery warning never goes off.

### Mappings, remapping and raw sticks (IN-17, IN-18, IN-19)
- Tested: `SDL_AddGamepadMapping` does not tell whether it added or updated; read it back with `SDL_GetGamepadMappingForID` and compare (ignoring `platform` and `crc`). When the environment variable `SDL_GAMECONTROLLERCONFIG` has a mapping for the same GUID, Add still succeeds but reads back the environment's mapping, so `MappingStatus.Applied` relies on the read-back.
- Tested: `SDL_ReloadGamepadMappings` drops every run-time mapping and also reads the file that `SDL_GAMECONTROLLERCONFIG_FILE` names: first rewrite the file to what should stay, then Reload. Controllers that stay get `REMOVED` plus `REMAPPED` (no `ADDED`), so events cannot be handled by name: first check whether `SDL_GetJoysticks` still lists it, then `SDL_IsGamepad`, or the controller is lost. A controller whose mapping did not change gets REMAPPED too: when the mapping text is the same, no `DeviceRemapped` is sent, or a modifier held on another controller would be reset and released.
- Tested: SDL sends no releases when it remaps, so a remap must be treated as a reset (`DeviceRemapped`, the router sends `Edge{Reset: true}`); otherwise Space stays held.

## go-sdl3 and purego

- **go-sdl3** v0.1.1 (purego, no cgo): the wrappers of `SDL_GetGamepadSensorData`, `SDL_GetGamepadTouchpadFinger` and the GUID getters panic outright, and there are no HID bindings. `internal/input/sdlext*.go` fills them in (looking the symbols up on the same path go-sdl3 loaded), including `SDL_hid_open_path/read_timeout/close` (IN-30).
- **purego and locked threads**: in v0.10.0, the call trampoline on unix/amd64 overwrites the g0 stack frame, and in a cgo build a thread that made a purego call crashes with SIGSEGV when it exits; a goroutine that locks its thread and returns without unlocking makes the thread exit (T-output and the slot loop both do this). Fixed from v0.11.0; we use v0.11.1, and `inputtest.TestLockedThreadExit` guards it.

## Keyboard output and layouts

### Keyboard injection
- **SendInput**: on amd64 an `INPUT` is 40 bytes. Use `KEYEVENTF_SCANCODE`, and add `EXTENDEDKEY` for keys with the E0 prefix. F13–F21 are scan codes 0x64–0x6C, F22 0x6D, F23 0x6E, F24 0x76. `KEYEVENTF_UNICODE` is for text only.
- **The dwExtraInfo tag**: injected events carry `"padm"<<32 | nonce` (`output.ExtraInfo`). The keyboard LL hook receives the full 64 bits, and tests rely on it to swallow only the events with their own nonce.
- **Special keys** (tested): Pause is sent as VK_PAUSE (wScan 0x45); the numpad 0x47–0x53 is translated by NumLock, so Num0–9 and NumDecimal are sent by VK; for the navigation keys, PrintScreen and Pause, `MapVirtualKeyEx` returns scan codes that differ from the physical keys', so they cannot be derived from it.
- **Menu masking** (tested): before a lone Alt or Win goes up, MenuMask inserts a press and release of vk 0xE8 in the same batch. The mask key enters neither the Arbiter nor the ledger; `padmatectl send` and injecttest do not go through MenuMask.
- **UIPI**: injecting into a window of a higher integrity level fails silently; it is only detected and reported (OUT-12), never bypassed. Win+L and Ctrl+Alt+Del cannot be injected.

### The held-keys log (OUT-14)
- The log is written before each SendInput with a new press. "A temporary file + MoveFileEx" takes up to 7.5 ms, so the log is rewritten in place on an open handle: `heldfile_windows.go` calls CreateFile itself (without `FILE_FLAG_OVERLAPPED`) and uses `windows.WriteFile` with an OVERLAPPED offset; the OVERLAPPED, the count and the buffer live in a struct on the heap, since local variables would escape and allocate (`TestHeldLogNoAllocs`).
- A test's heldFile must be in TempDir, never `%LOCALAPPDATA%\padmate\run\held.bin`, and the test must also set KeyDown (`liveConfig.keyDown`, `LoopOptions.KeyDown`), or the sweep reads the machine's real keyboard state.
- **The identity in the log's header**: `GetAsyncKeyState` cannot tell injected from physical presses, and a log left by another boot or sign-in session would release keys the user is holding now, so only a log of the same identity is swept. The identity is the LUID plus the sign-in time (`LsaGetLogonSessionData`), compared bit for bit; do not use "now minus `GetTickCount64`" (the clock jumps and drifts after sleep). A test's log must carry the same identity as the Loop (`output.EncodeHeld`).

### Rules for tests with real injection
- **LL hook timeout** (by Microsoft's documentation, not tested): when the hook procedure times out (LowLevelHooksTimeout, at most 1 s), that key is not swallowed, and the hook may be removed silently, after which every injected key reaches the foreground program. So fence every batch and stop injecting on failure: use `InjectFenced` (`InjectFencedMixed` with mouse events), and the O(1) `WaitOwn` for many batches (ARCHITECTURE §14).
- A swallowed CapsLock, NumLock or ScrollLock still flips the system's lock state; tests press them in pairs.
- **A mouse button press can never be injected alone**: if the hook does not swallow it, it is a button held on the screen. Put the press and the release in the same batch (`InjectFencedMixed`), with the canary at the end of the batch; an unpaired batch is refused before anything is sent. `InjectFenced` refuses batches with mouse events.

### The mouse
Tested on Windows 11 x64.

- **Buttons can be held**: every exit path must lift them; the held-keys log uses the slots of VK 0x01, 0x02, 0x04, 0x05 and 0x06. Pressing a button again while it is down makes the app see half a double click, so the Arbiter never presses twice, and profiles refuse hold together with typematic repeat. `GetAsyncKeyState` cannot tell an injected mouse button from one held physically, so the sweep may inject a release for a left button the user is holding.
- The mouse LL hook (`EnableMouse`) calls its procedure for every movement: it first asks `MouseOptions.Watch`, and events it does not care about go straight to `CallNextHookEx` (not copied, not queued, not swallowed); otherwise the physical mouse would lag. It is installed on the keyboard hook's thread; unhooking removes the mouse hook first, then the keyboard. In the hook, `dwExtraInfo` keeps only its low 32 bits, so `output.IsPadmate` is always false for mouse events; compare the low 32-bit nonce instead (`Recorder.mouseOwned`).
- **The mouse canary** (tested): a WHEEL with `mouseData` 0 and a MOVE with dx=dy=0 make SendInput return 1, but the hook never sees them. So the canary is a pair of relative moves with the nonce (+1 then -1, `MouseCanaryEvents`); it counts only when both arrive and are swallowed. If they get through, the cursor moves one pixel and back. A canary nonce is used for one batch only.

### Pointer movement
- `dx` and `dy` are amounts of movement, not pixels: the system scales them by "pointer speed", and with "Enhance pointer precision" on they also go through the acceleration curve (tested: +300 → +600). padmate does not change these settings; the unit of `mouseSpeed` is SendInput's movement. A movement with both `dx` and `dy` 0 never reaches the hook, and the engine does not send one.

### Media keys and typing text (OUT-20, OUT-21)
- Media keys are sent by VK, with the E0 scan code in `wScan` and `EXTENDEDKEY`, without `SCANCODE` (`KeyEventFor` gives `ByVK`); they are ordinary keys that can be held. If a test does not swallow one, the volume or the playback state changes; while recording a shortcut, the capture hook does not swallow physical keys, so recording a volume key changes the volume.
- A Unicode event's press and release go in the same Send, and enter neither the Arbiter's key table, the held-keys log nor the startup sweep. When a send partly fails, the release is sent again at once; if that fails too, it goes to `Arbiter.stuck`, which `ReleaseOwners` sends and `Held()` counts (invariant 1).
- Tests must never inject a Unicode press without `UnicodeCanary` (one that gets through is a character typed into the foreground window): first inject the release of U+FFFF, and only once the hook has swallowed it, the press.

## Win32 and message loops

- **Win32 bindings**: generated with mkwinsyscall; never write `NewLazySystemDLL`/`NewProc` by hand. Each package writes `//sys` lines in `syscall_windows.go`, and `task gen` generates `zsyscall_windows.go`. The generated functions return `EINVAL` when the last error is 0, so judge failure by the return value. DLLs and functions are loaded on the first call (which allocates), so call outside a hook callback, once, what the callback will call (`winhook.Start` calls `latency.Now` first).
- When the last GUI thread of a process exits, Windows destroys every window class, after which CreateWindowExW fails with "Cannot find window class"; so winsession registers its window class on T-session on every Start.
- **padmate's own windows are a foreground too** (UI-18): while the tray menu or the Electron UI is open, it is the foreground, and without filtering the profile would switch to the default one. padmated filters by its own PID; a registered UI keeps the current profile and releases nothing (OUT-25), and `app.foreground` is published as usual with `own:true`. Tests call `onForeground` with a fake `winfocus.App` and never change the real foreground.
- **The tray**: `fyne.io/systray` must run on the main thread.
  - "Open window" starts `padmate.exe` only in the installed build: a development or test build that started it would open the app with real data and `--inject`. Double clicks (DMN-05) are counted by `tray.Taps`; do not block in Tap. The cleanup worker must not call systray's Quit (onExit is nil before Register); it only posts WM_QUIT to the main message queue. Failures, panics and unexpected returns from the loop must keep a non-zero exit code.
- **The real foreground changes a test's profile**: a library-mode test with the real winsession/winfocus picks a profile by the real foreground about 50 ms after starting, and an unbound foreground replaces `--profile-id` with `default`. Such tests write `{"schemaVersion":0,"enabled":false}` in the data folder; tests of selection use the fake foreground of `startSelectionLive`.
- **The security descriptor of a named event** (DMN-20): `CreateEvent(nil, …)` uses the default DACL of the creator's token. By the UAC documentation (not tested), the default DACL of an elevated token grants only Administrators and SYSTEM, so a non-elevated process of the same user cannot open it with `EVENT_MODIFY_STATE`. So `emergency.Listen` sets `D:(A;;0x1f0003;;;<user SID>)S:(ML;;NW;;;ME)` explicitly (`TestListenSecurity`). When the event already exists, `CreateEvent` returns a valid handle together with the error ERROR_ALREADY_EXISTS; check the handle first, or it leaks.

## Pause, system events and exit

Tests of what happens while the screen is locked, during sleep or sign-out use only fakes, virtual gamepads and `internal/winsessiontest`; they must never really lock, sleep or sign out the machine. `winsessiontest` refuses `HWND_BROADCAST`, other processes and windows of other classes.

### Suspend and resume (DMN-09, DMN-12)
- **Synthesized releases and late holds during a suspend**: while the screen is locked or the machine sleeps, SDL may first send a synthesized up, and the down of the original hold arrives late, after unlocking. The router quarantines buttons and axes active before and during the suspend, each on its own: an up or a return to center during the suspend, and an empty `DeviceState`, do not lift it; after resuming it must see active → release/neutral once more, and time cannot lift it. Axes first moved during the suspend, and controllers that connected while suspended, are quarantined too, so after resuming a stick has to return to center and be pushed again before it maps; this is by design. A known gap: for a button pressed only during the suspend, with no event at the time, a late down cannot be told from a new press after resuming. The model of FuzzRouter must judge neutrality by the same rules (`frNeutral`, `axisApplies`); change it together with the analog settings. `Supervisor.Suspend` is not in the event order, so the fuzz's `frSuspend` first sends a `removed(0)` of an unknown controller to make sure the previous event has been routed.

### Pause and the emergency combo
- **Where it is detected, and on which thread**: `input.ComboWatch` sees an event on T-input before it goes into the channel (so it also sees events a full channel drops); do not move it behind the channel. `OnCombo` runs on T-input and may only call `output.Loop.Block`, never `Do` (which waits for T-output). `ComboHeld` is not written to traces; golden tests and `--fake-input` insert it with `input.ExpandCombos`.
- **Pause edges** are delivered through `Edge.Pause`, and every edge during pause carries PauseOn. Only starting new slots paused is not enough: a press queued before a restart would be replayed after resuming (`TestPauseRestart`).
- **Changing the emergency combo, and lock order** (UI-19): when config.json's `safety` changes, call `ComboWatch.Repick` on T-input only through `Source.RepickCombos`; do not touch ComboWatch from another goroutine, and do not reopen the Source to change combos. In `commitConfigLocked`, take `configApplyMu` before `profileMu`; the other way round deadlocks.

### Exit
- **Sign-out, shutdown and SIGTERM** (by the documentation, not tested): the GUI-subsystem release build receives no console events; padmated learns of them from `WM_QUERYENDSESSION`/`WM_ENDSESSION` in the winsession window. About 5 s after `WM_ENDSESSION` returns, the system ends the process, so it waits at most 3 s. When T-session called `OnStop("session-end")` (`liveRun.sessionEnding`), the shutdown log is written before T-session closes; otherwise T-session closes first, so the final log lines are not lost. taskkill without /F sends WM_CLOSE, which is handled as a stop; with /F there is no chance, and the release relies on the held-keys log of OUT-14.
- **The limit on input cleanup after the release** (DMN-10): after the supervisor's Run and `Loop.Stop` have finished releasing and retrying, the feedback/input tail shares a limit of 1 s; never wrap a timeout around the key release. On timeout, call the non-blocking `Source.RequestClose` (`SetFeedback` may wait for a stuck T-input). A timeout, or a panic/Goexit of the cleanup worker, logs an error and returns 1, and the final log is still written and the session window closed; a late cleanup must never reopen output.
- **Waiting on tray exit** (DMN-22): close the `output.BlockExit` gate first, then wait (2 s) for the UI to finish saving; presses during that time send no keys, and the gate has no way to reopen. IPC keeps serving, and `profiles.put` and `config.put` still write to disk. `ui.exitReady` is matched to the session that `Hub.PublishSync` returns; do not use a name the client reports.
- **The installer needs the daemon to exit** (PKG-04):
  - `Endpoint.Close` deletes `daemon.json` as soon as the daemon starts stopping, so `padmatectl quit` opens the process by pid before it sends the request. The pid may be stale or reused, so quit checks that the image name is `padmated.exe`; the installer passes `--under <installation folder>`, and a process whose image path is outside it is neither asked nor waited for (`daemon.json` may belong to a development build or a portable copy). `padmatectl ui-bridge` (a child process of the UI) holds `padmatectl.exe`, so a reinstall or an uninstall must make the UI exit first (`daemon.exiting`).
  - `release-all` cannot replace quit: it makes every `--inject` padmated of the user (including ones installed elsewhere) release its keys and destroy its scripts. Use it only when quit fails, and never under the `PADMATE_INSTALLER_TEST_ROOT` override. If after 10 seconds a `padmated.exe` is still in the installation folder and `release-all` has not run, run it once before ending the process, because `TerminateProcess` does not release held keys, and a full uninstall deletes `held.bin` as well.

## Engine, slot and supervisor

- **runtime.Goexit**: while Goexit unwinds, `recover()` in a defer returns nil, so a flag is needed to tell it from a normal return. `output.Loop` and `slot.RunLoop` both do this and still release the keys after Goexit; the supervisor treats a Goexit of the slot loop as a panic and restarts the slot.

### Scripts with the slot and the supervisor
- **The edge barrier of the first setup**: for a profile with a script, the supervisor sends a Resync on every assign, and the candidate starts only once the slot has finished the Resync; otherwise the worker may read `pad.isDown` from the old all-released state. When a hot reload adds a script, the slot must open the first-start gate with the snapshot it has.
- **Persistent layers and release (PRO-11)**: exit, profile switches and disconnects must save the selection before canceling controls, or CancelAll clears the toggles and an empty state is written back. LayerMemory does no disk I/O; leaving the loop calls `preserveLayers` first, and the flush comes after the keys are released. Restoring does not include hold/latch.
- **Scripts consuming one edge (SCR-05)**: the slot must not send ButtonDown/Up separately by what was consumed; consuming only the release leaves a declarative hold behind. Scripts are resolved at the state transition of the engine's `stepButton`, and physical and virtual controls take the same path. A script's `pad` may only use the snapshot the slot loop copied.

### The Arbiter's timing and the event-gap queue (OUT-10, OUT-11, OUT-17)
When `SetEventGap` is above 0, the Arbiter queues the key events of a command and sends them a gap apart. Go through this list before changing the Arbiter in `internal/output`; each item has a regression test or fuzz corpus.

1. **Failed releases and forced release**: after a release and its retries fail, refs is 0 but the physical key may still be down; while the key is still in the ledger, a queued tap of the same key must wait. A queued press that was displaced may already be down, so its release is sent as usual (`mayBeDown`). Releasing only modifiers triggers an input-method switch, so the mask key is inserted before the first modifier goes up.
2. **Shared presses are counted per owner**: a press not yet sent may be borrowed by another owner, so keyState records `users` and drops the key only when all have released; otherwise someone else's Ctrl+X becomes X. The queue cannot grow without bound: Repeat and taps on a held key queue at most one extra press per key, and Downs alternating faster than the gap merge into the last one (`mergeDown`, `MergedKeys` in the fuzz). Releases enter the queue in their order without gap (`zeroDeadline`); queuing them only after the press goes out would hold two combinations at once.
3. **A canceled tap must not leave a hold**: a tap's hold first goes into `ref.minPress` and joins `minHold` only when it ends normally; otherwise, after a forced release cancels the tap, a key held by another Down stays held past its Up, and Ctrl+Num1 becomes Ctrl+Alt+Num1 (`TestEventGapCanceledTapHold`). Timing comes only from the profile, not from `PADMATE_BENCH`; `slot.Advance` runs the Arbiter first, then the script, then the engine.

### Gestures and buffering (MAP-06, MAP-07, MAP-09, OUT-11)
- **Gestures that fire on release cannot hold** (MAP-07): `commitMulti` runs the action on a copy of `e.multi[c]` and then drops the copy, so a `Down` combination, repeat or held layer would have nobody to end it (invariant 1). So release, tap and multi-taps can only use tap mode, cannot have repeat, and their layer actions cannot be hold; `profile.Parse` and `engine.Compile` both check this (`TestParseAndCompileAgree`). A new gesture either runs on `e.ctl[c]` or adds the rule in both places. Bindings returned by a Level of `Options.Registry` do not go through Compile; check them with `engine.CheckBinding` first.
- **Edges in the buffer cannot be overtaken** (MAP-09): while the buffer is not empty, new edges (including releases of controls already dispatched) go to the end and are replayed in their order. Overtaking an edge of the same control leaves a key stuck; overtaking another control's reorders them (a modifier released first loses the combination, a multi-tap window is committed early). A Pending control's own release cannot overtake either: when the drain decides on a tap, only the tap action runs (`decideTap`), and the release stays in its place.

### Analog controls and sticks
- **Ask the engine for stick settings, not the Program** (IN-14): calibration lives in `Engine`; read it with `Engine.Analog()`. A calibration change must not CancelAll (dragging a slider would release keys); it goes through `settleVirtual(now, false, false)`, and `Reset` does not clear the calibration. `configNeedsRestart` compares only the ignored devices; otherwise every slider drag would ask for a restart.
- **Sticks in mouse mode**: after `CancelAll`, a stick still pushed has to return to the dead zone before it moves again (`mouseLock`); `Reload` and calibration changes do not lock it, or the UI's autosave would stop the pointer. An `inputOnly` engine has no `Output`, so it cannot call `Output.Move`/`Jump` or schedule deadlines.

### The function key (MAP-27, `engine/function_keys.go`)
- The edges of the function key (`Program.fnKey`, one of `back`, `start` and `guide`) return in `stepButton` before `inputOnly`, `Options.Button` and the buffer, so `e.ctl[…]` is never pressed for it. `st.down = e.physical[c]` in `cancelAll` must leave it out; a `Reload` that changes the function key must clear the new function key's former `e.ctl[…]` and `fnActive`. A buffered edge carries the function key in effect when it arrived (`Input.fn`); do not read `e.fnActive` in `press`.

### Sequences, decisions and fuzzing
- Canceling a sequence marks the sequence before canceling taps and text (`cancelQueued`: `endSeq` first); otherwise one more step goes out. `TapSequence` (an array of KeySpecs) does not queue and runs in parallel with other owners, which golden outputs depend on; `Sequence` waits for the earlier ones to end, and `engineOutput.TypeText` must go through `Sequence`. A wait in a sequence counts from the physical release of the step before, and does not add the `gap`.

- **A remap does not clear a pending quarantine**: `router.remapped` clears only `d.state` and `hasSnapshot`, not `d.recovery`. A change that cleared `d.recovery` passed the unit tests, the golden files and the corpus alike; the last four seeds of `frSeeds`, which cross a remap, each kill one such change, and they must keep passing.

## Latency and timing

The design of end-to-end latency is in [ADR: Engine and threads](adr/0005-engine-and-threads.md).

- **Windows timing**: `time.Now` jumps only every 0.5–2 ms; for microseconds use QPC (`latency.Now`). Go's `time.Sleep(1ms)` actually takes about 1.05–1.6 ms; Win32's `SleepEx(1)` usually about 15 ms. A test that requires "an interval measured with QPC is at least some wait" cannot use `time.Sleep`; spin on `latency.Now` instead.
- **SDL clock** (ENG-11): `SDL_GetTicksNS = (QPC − tick_start)·1e9/freq`, so `Event.Time` can be converted back to QPC: `Source.SampleTicks` takes readings, and `latency.CalibrateSDL` finds tick_start. Tested: SDL's counter frequency equals QPC's (10 MHz).

## Scripts

The decisions are in [ADR: Scripting runtime](adr/0010-scripting-runtime.md).

### goja, esbuild and types
- **goja** (SPK-03): supports ES2015+ and async/await, but not ESM, top-level await, async generators or for-await, so esbuild bundles to an IIFE. A Runtime can be used by one goroutine at a time. The feature table is `internal/script/compile/goja_features.json`.
  - `Runtime.Interrupt` has no effect inside a native Go function, so host APIs must return quickly. An Interrupt sent while no call runs makes the next call fail at once, so every call ends with `ClearInterrupt`.
  - `Object.Get` returns Go's nil for a missing property: an array with holes gives nil at an index, and calling `.Export()`/`.String()` on it panics and restarts the whole slot. Check for nil before reading the elements of an array a script passes (`stringValue` in `hud.go`).
- **esbuild**: `TsconfigRaw` must be set, or it reads a tsconfig.json outside the root. A computed `import()`/`require()` path is expanded as a glob without going through OnResolve, so OnLoad has to check again.
- When the `padmate` module gains a value member (like `hud`), `padmateStub` in `compile/plugin.go` must export it too; otherwise `import { hud } from "padmate"` fails to bundle, while tests that only exercise the runtime still pass.
- **The script API version is kept in four places**: `dtsgen.SupportedAPIs` (the current version first; `HostAPI` is the first entry), the `script.api` enum of `schema/profile.schema.json`, `apiVersion` in `internal/script/host.go`, and `@since`/`@until` in the d.ts. Tests align the first three; after changing the schema's source, run `task gen` for the copy. A new value member of the d.ts must go into `StableMembers` or `PreviewMembers`, and members macros can use (`@macro`) must be stable. When a new version changes a member of the previous version, it needs a shim and a consistency test. After raising the version, fixed profiles that were not raised get one more `/script/api` warning, which breaks "zero diagnostics" assertions (find them with `grep -rE '"api": ?"0\.N"'`).

### Macros (SCR-50)
- **Output scope**: a normal end cannot use `ReleaseOwner` (it would cut short a last tap that was not awaited, and release keys of other owners); it lifts with `Up` one by one. Only the 60-second limit and the safety boundaries use `ReleaseOwner`.

### The watchdog
- **QueryThreadCycleTime** counts TSC time; sleep does not count, and migration causes no jumps. At startup it is calibrated against QPC (10 busy waits of 1 ms per group); the loop must not call `runtime.Gosched()`, which lowers cycles/µs and makes 900 ms of script CPU time look like more than 1 s. `GetThreadTimes` has a granularity of 15.6 ms and is not used.

### Lifecycle, pause and profile switches
- **Pause cannot just ReleaseKeys** (SCR-04): `every`, `sleep` and Promise continuations would still press keys again through `RunDue`. Pause must invalidate the old Host and refuse candidate swaps, and resuming rebuilds on the worker; an initial pause must take effect before the factory builds, or `onActivate` has already produced output.
- **Owners, teardown and invalidation** (SCR-04): the cycle is shared by the whole scriptRuntime, so a new `Lifecycle` must not start numbering again from Cycle 1; otherwise `Dispose.ReleaseOwner` of a canceled old candidate would release new keys of the same slot and gen. The slot loop releases the old Host's owner first, then disconnects the output sink, and only then lets the worker run the teardown. When the first Send of an offline emergency release fails, the supervisor still completes the ReleaseAll barrier of every slot before reporting the combined error; otherwise an old every/sleep presses keys again once the gate reopens.
- **Profile selection and hot reload**: changing the profile key must stop the old lifecycle before the engine is replaced and layers are restored, and must not take the hot-reload path that keeps the old script; otherwise, when the new script's setup fails, the old profile's every keeps sending to the new foreground. The old teardown also must not write the old layer selection into the layer memory of the new ID (`TestProfileSwitchDisposesOldScriptWhenNewSetupFails`).
- **Effects are canceled by (class, controller), regardless of which runtime started them**: while an old and a new runtime both exist (`Lifecycle.Swap`, `pollReload`), an old cancellation that arrives after the new `onActivate` started its effects would end them too, so both places call the old Host's `CancelEffects()` before the new activation.

### Output
- **Tap completion crosses threads** (SCR-06): the callbacks of `output.Loop` run on T-output and may only post to a queue and wake the slot; they cannot call goja or `Host.RunDue`, or call the Loop again. Pause, unloading and destroying disconnect output first and abandon the old Promises; `Host.Dispose` must abandon old tap Promises before the teardown.

## Files, builds and tools

### The repository and command-line tools
- The Go module is in `daemon/`: `app/node_modules` has npm packages with `.go` files, which would break `go build ./...` at the root. SDL3.dll is not committed; its version and SHA-256 are pinned in `internal/sdlpin`. go test runs in the package's folder; `PADMATE_BENCH_DIR` must be an absolute path that exists.
- **The bytes of profile fixtures**: fixtures with CRLF, invalid UTF-8 or UTF-16 are marked `-text` in `.gitattributes`; otherwise `* text=auto eol=lf` may change their line ends. Add new fixtures of this kind there too.

### The file system
- **Replacing a file by rename** (tested): when the target has an open handle without `FILE_SHARE_DELETE` (Go's `os.Open` and `os.ReadFile` open such handles), `os.Rename` on Windows fails with Access is denied. Tests that save a profile by rename must retry, since the watcher may be reading it. `profilelib.WriteScript` retries 10 times on ErrPermission, 20 ms apart, and keeps the old file if it still fails. Deleting fails the same way: when a save deletes the oldest snapshot (PRO-17), it avoids files this process is reading, and files another program has open are left for the next save.
- A plain `RemoveAll` of a profile folder that meets a file in use deletes half of it and leaves a broken profile without profile.json: `profilelib.Remove` first renames it to a hidden `.tmp-<id>-*` under the write lock and then deletes it (UI-17). Creating `abcdefghij.ts` also gives it the NTFS short name `ABCDEF~1.TS`, after which an exclusive create of `abcdef~1.ts` fails with ErrExist, so export and import both refuse entries that look like short names (`isShortNameLike`).
- **Imported files have no mark of the web**: extracted files have no Zone.Identifier, so SmartScreen no longer warns. Exports accept only scripts, JSON and text (`archiveFileProblem`); before adding a type, make sure Explorer would not run or follow it (.lnk, .url, .library-ms and `.{CLSID}` folders all would).

### The profile library and the settings files
- **The profile library** (PRO-05/06): read files with `Library.Read` (`os.Root` plus a 4 MiB limit). Migrated output exists only in memory and must keep the document's length (padding with spaces when an old version's notation is longer), because validation runs on the migrated text while diagnostic offsets are reported against the original. Writes with a revision (PRO-14): profile/config/state share one lock, and the check and the rename happen in the same critical section; an empty revision means only "does not exist"; the new revision that `profiles.put` returns means only that it was saved, while applied/problem say whether the runtime accepted it.
- **Reloading and writing back with inheritance** (PRO-19): a parent's watcher marks new content as seen once it has read it, so if `reloadDependentFor` gives up when it cannot read a child, that change is lost for good. When an operation that "writes first and then renames the folder" fails, it writes back with `undoLocked`, leaving no snapshot; with `putLocked`, every failure would leave two snapshots, and a few would flush out the limit of 30. When another profile's profile.json cannot be read, deleting a profile treats it as not a child, while renaming and deleting a macro refuse, since the unreadable one may refer to that macro.
- **The script library and migrations** (SCR-51): migrations rewrite a profile's references at their byte positions and never serialize profile.json again; every step must be safe to run twice (write the new file before deleting the original; write profile.json only when the revision matches). A profile.json that cannot be read, or that was changed, must not be renamed by force, or that profile would run another script of the library under the old name; when any write of `macros.rename` or `macros.delete` fails, what was written is changed back.
- **Automatic repair of the settings file** (PRO-29): an error reading config.json writes to disk (the backup plus the replacement), so tests always use a temporary data folder. When the replacement fails, the backup is deleted, the repaired settings stay in memory only, and the same file (by revision) is not tried again. A replay (`--fake-input TRACE`) never writes to disk: a new entry point that reads config.json must first ask whether it is a replay. A config.json that cannot be read (a folder, access denied) is still a startup error; bad JSON only triggers the repair dialog.
- **Importing AntiMicroX files** (PRO-21, `internal/amgp`): an AntiMicroX set replaces the whole set, while padmate's overlay layers fall through to the layers below, so in a layer that holds a set, controls without a binding must be written as `block`; a return button that `while-held` points back at set 1 does not count as a held target, or the base layer would be blocked as a whole. Text from the file goes through `shorten`/`clipText`/`cleanText` before entering the report, or it could write line breaks that forge report lines. Times that keep a key held must have a limit (invariant 1): a file with a `turbointerval` of 2147483647 can make a key held for dozens of hours, so the related values are all limited to `maxKeyDownMs` (10000). Real files under the GPL or without a license do not go into the repository; they are tested locally only, through `PADMATE_AMGP_CORPUS`.

### IPC and starting the daemon
- The second instance (DMN-14): a repeated start reads no state/config, opens no local log and no SDL, and forwards once over authenticated IPC; explicitly conflicting startup arguments are refused, and a dry-run request must never switch an inject process. A bare `--fake-input`/`=ipc` is always a dry run, and the arguments of start at sign-in must keep the fake flag.
- IPC: the `OnNotify` of the jrpc2 client does not keep order, so the callback only puts into a bounded queue and must not call the client; an overflowing subscription queue must fail explicitly; the token must be protected by an ACL from the moment the temporary file is created. The daemon fails the whole subscription for a topic it does not know, so when the UI's `subscribe` meets that, it subscribes again without `daemon.exiting`; new topics must step back the same way. `Hub.Publish` runs `json.Marshal` on the caller's goroutine, so callbacks on the hot path (slots, the router, T-output) must not publish large payloads directly; decision events go through `decisionFeed`.
- **The length of the start-at-sign-in command** (DMN-08): a successful Run registration does not mean an overlong command will run at sign-in; the limit is 260 UTF-16 units. Long arguments are referenced by content in a fixed startup folder of the user, and turning start at sign-in off does not delete the argument files. A real GUI sign-in may have no standard handles; when `stdout.Stat` fails, the dry-run printer writes to `io.Discard` instead, and must never switch to inject because of it.
- **Development builds never write start at sign-in** (UI-19): the daemon of the development UI and test builds have a tray too, and once could overwrite the real HKCU Run value. There are two checks: `newStartup` creates no startup entry in these builds, and `startupControl` uses only test startup entries that implement `memoryEntry`. Keep both when changing the tray, the startup RPCs or the startup code; tests use fakes and never call `autostart.New`.

### Packaging and the installer (PKG-*)
- **Never start the installed `padmate.exe`, or the one in `win-unpacked`, directly** (PKG-03): it uses the real `%APPDATA%\padmate`, and its daemon runs with `--inject`, sending real keys to the foreground. Automation goes only through the test mode: `PADMATE_UI_TEST_PACKAGED=1` plus three private folders, `PADMATE_UI_DATA_DIR`, `PADMATE_UI_IPC_DIR` and `PADMATE_UI_USER_DATA`; missing any one means it is the real app, so scripts set them together and check them afterwards. The release daemon becomes a private instance through `PADMATE_PIPE`/`PADMATE_IPC_DIR`, which are set only in tests.
- `INSTALLER_BIN=DIR` builds padmated and padmatectl elsewhere; otherwise electron-builder overwrites the exes of a running development build. electron-vite treats `dependencies` as external by default, while the installed app has no node_modules, so `externalizeDepsPlugin` must exclude electron-updater.
- **The smoke test must not use `--force-run`**: with it, the template of a silent install makes Explorer start the Start menu's `padmate.lnk`, and the new `padmate.exe` does not inherit the test's environment: it is the real app. `runCommand` in `installersmoke` refuses it. An update-style reinstall uses `<installer> --updated /S`, without `/D=`. Whether a process still runs is judged by the exit channel of `cmd.Wait`, not `OpenProcess` (process ids are reused).
- Certificate entry points: with `WIN_CSC_LINK` or `CSC_LINK` in the environment, even an "unsigned" build gets signed, so `signingPlan` sets the certificate variables it does not use to empty strings (deleting them is not enough: the CLI fills them in again from `app/electron-builder.env`). Signing modes always set `DEBUG` to an empty string (it would echo the signtool command line, including `/p password`), and the output of signing builds is filtered line by line through `redact`. `SDL3.dll` is not signed (`CheckTree`'s fixed hash).
- **The installer smoke test writes real state** (SPK-07, `task test:installer`): it temporarily writes the real `HKCU\...\Uninstall\<GUID>`, `HKCU\Software\<GUID>` and the Start menu's `padmate.lnk`, and deletes them at the end (failures included). It refuses to run on a machine where padmate is installed or `padmate.lnk` already exists. Everything else points to test folders through `PADMATE_INSTALLER_TEST_ROOT`; do not run `*-setup.exe` by hand. padmated in the tests always runs with `--dry-run --tray=false`. The wizard cases click real windows, and "Run padmate" on the finish page is checked by default, so each case must clear it first.
- **Shells inside the Claude desktop app see a virtualized registry and AppData**: the desktop app is an MSIX package, and the shells and child programs it starts (`task test:installer` included) write HKCU into the package's own registry, and `%APPDATA%` and `%LOCALAPPDATA%` into `%LOCALAPPDATA%\Packages\Claude_pzs8sxrjxfjjc\LocalCache\`; reads merge both. So `Get-ItemProperty HKCU:\…` and `reg query` may not show the real keys. Read the real registry through WMI: `Invoke-CimMethod -Namespace root/default -ClassName StdRegProv -MethodName GetStringValue -Arguments @{hDefKey=[uint32]2147483649; sSubKeyName='…'; sValueName='…'}` (`ReturnValue` 0 means read, 2 no such key, 1 the key exists but not the value); real files through `Get-CimInstance CIM_DataFile`. Do not conclude that the installation is broken before reading it through WMI.

### Signing and PE checks (PKG-09, PKG-11)
- electron-builder signs `padmate.exe` before `afterSign`, and `stamp-exe-version.mjs` has to change it: the hook reads it with `ignoreCert`, writes the version, then calls `context.packager.signIf(file)` to sign it again. When `signIf` is skipped it returns `false` instead of throwing, so the hook throws itself when `forceCodeSigning` is true and the result is `false`.
- **signtool leaves a private key file behind when it imports a PFX** (tested): each `signtool sign /f x.pfx` leaves one more CNG key container in `%APPDATA%\Microsoft\Crypto\Keys`, even after the PFX is deleted. `test:sign` recognizes them by content and deletes only the ones not there before it ran; the certificate is made in memory, without `New-SelfSignedCertificate`, which would write to the certificate store.

### Automatic updates and the download site (PKG-10)
The update source is `https://padmate.download/` (Cloudflare R2 plus a Worker); electron-updater uses the generic provider.

- **The download site**:
  - Upload order: the installer, the `.sha256`, and last `latest.yml`. A published installer is never overwritten or deleted (`latest.yml` carries its SHA-512, and Cloudflare caches `.exe` by default); a fix means a new version.
  - `publish` in `electron-builder.yml` must set `channel: latest`: without a channel, the generic provider takes the first prerelease identifier of the version as the channel, so `v1.0.3-rc.1` bakes in `channel: rc`, and clients ask for `/rc.yml`, which R2 does not have.
- **Electron's single-instance lock is per userData folder**: call `app.requestSingleInstanceLock()` after `app.setPath("userData", …)`. A second instance calls `app.quit()` while its modules load, so the `whenReady` callback must first check whether it got the lock, and not start a daemon.
- **electron-updater 6.8.9** (check again when upgrading): `autoDownload` and `autoInstallOnAppQuit` default to true (the latter quietly runs the installer and stops the daemon when the UI closes); both must be turned off explicitly. The setter of `channel` sets `allowDowngrade` to true, which we never set. `quitAndInstall` starts the installer first and then calls `setImmediate(app.quit)`, so the UI must save before calling it.
  - The token that writes to the bucket must never get into the repository, `electron-builder.env`, `release.yml` or a log.

## UI

The design is in ARCHITECTURE §12, the decisions in [ADR: Editor UI](adr/0013-editor-ui.md) and [ADR: Overlay](adr/0014-overlay.md).

### Processes and security
- **The packaged UI sends keys**: when `app.isPackaged`, Main starts the daemon with `--inject`; the development build, the harness and E2E use `--dry-run` (`runtime-options.ts`). Automated tests use the development build only. The daemon decides the start-at-sign-in command; the UI passes only a boolean and never builds the exe and arguments.
- **Development isolation**: `task app:dev` uses a private daemon in `.cache/ui-bin` and data in `.cache/ui-*`; isolating only the data folder while still connecting to the user's discovery folder, pipe or mutex is not enough. The daemon must be in a layout that `ownwindow.TrustedPaths` accepts, or `ui.register` is refused. When an exe is in use, check its path before closing the matching instance; never kill by process name.
- **The Electron security bridge**: the renderer has no Node and no discovery token. Main connects to the pipe through `padmatectl ui-bridge`, and shows the window only after the first UI registration succeeds; registration cannot be skipped, and not every electron.exe counts as this program.
- `webContents.send` has no back-pressure, so Main limits the batches in flight and the preload acknowledges what it consumed; when navigation starts, sending pauses and old batches are reclaimed, resuming only after `did-finish-load`. New IPC topics are added on both sides together (`ipc-wiring.test.ts`). The report on the startup failure page is written by another program, so Main keeps only the fields it knows; for configuration backups, Main takes only the name the renderer gives, checks it with `validateConfigBackup` and builds the path itself.
- **Output to our own windows** (OUT-25): the protection must come before T-output's commands and timers; hiding output only in the page cannot stop SendInput. The transition gate opens only after the slot/script cleanup succeeds, and checking the transition generation and opening the gate happen within the same command on the output thread; a failed release keeps the gate shut, and a transition never re-sends keys that are held.

### The editor: saving and drafts
- **Saving with the single-set UI** (UI-39): the UI edits only `layers.base`, but the draft must be the whole profile, never rebuilt from the UI's model, or the other layers, common, layer actions, block, defaultLayer and the feedback settings would be lost. When defaultLayer is not base, the whole profile is read-only.
- Changes save at once (UI-43): a text field commits only on Enter or on leaving it (`useCommitField`), so tests must `blur` or press Enter after `change`. Changing the action type first gives a draft with empty parts, and what is saved is the `savedForm` without them. A reread caused by `profile.changed` may come after our own save; if the revision changed, read again.
- **A save without an answer may have been written**: when the bridge gives up on `profiles.put` after 10 s (with no code), the file may have been written while the revision is stale, and the next save gets a conflict. It must not be taken for a change made elsewhere and reread from disk, which would lose the edits made in the meantime. `editor-store` remembers the text of puts that got no answer (`unconfirmed`); if the disk content equals it, we wrote it. An error with a code is a clear refusal and is not remembered.
- **The daemon rewrites profile.json** (SCR-50, SCR-51): renaming, deleting and removing legacy scripts change the file directly in the daemon. Before the call, `flush()` waits for the write, and the call is not made if it cannot save; after it, `reload()` rereads the draft, and `clearHistory(id)` runs only when the `profiles[].id` returned include it. Changing only the revision would make the next autosave write the old name back; not clearing the undo history when it should be means Ctrl+Z changes the old name back.
- **Inherited content is for display only; writing back goes through `writeBack`** (PRO-19): `draft` is always the profile's own file; `withInherited(draft, parent)` adds the parent's content, for the controller picture, the button list, the sheet and the drawer to read only. Before giving a merged `Profile` to `state.edit`, call `writeBack(draft, parent, next)`, or one small edit copies the parent into the child. Everything that reads "the saved form" must pass `parent` to `savedForm`.

### The editor: buttons, the function key and sticks
- **A stick's two selection ids**: `leftstick` and `rightstick` are "rotation", `leftstick.press` and `rightstick.press` are "press", while the binding key `leftstick` is the binding of pressing the stick. A binding key finds its drawer through `calloutFor`, a selection id finds its binding through `bindingKey`, and comparing "is this callout the one selected" goes through `calloutOf` first; otherwise the "press" cell has no name and lights no leader line.
- **The function key's set** (UI-30): when the function key's set is edited, `swapView` swaps it into the place of `layers.base`, so all code that "looks through every set of buttons" must count `functionSet` in. Which button is the function key is decided by `functionKey` in config.json; the pure functions all take it as a parameter without a default, so never judge it by the control names `back` or `start`.
- **The mapping wizard's capture and cleanup** (IN-19): the wizard opens a capture that stays: window `blur`, locking the screen and sleep call `windowAway()` and do not stop it; closing, reloading, a renderer crash and exit call `stop()`; a disconnect calls `disconnected()`. Do not turn blur into `stop()` (switching to another program while the wizard is open would make the controller's buttons send shortcuts), and do not turn other paths into `windowAway()` (the window would be closed while mapping stays stopped).
- **Shortcut capture** (UI-19): start/stop/events all carry a session, and a start arriving late on unmount may only stop its own session; the hook only observes, and automated tests must never really press Win+L or Ctrl+Alt+Del or sign out. When recording the emergency combo, a `capture.start` that timed out or failed may still reach the daemon, and a `capture.stop` may not have gone out, so once `pad-capture.ts` has sent a start, it keeps sending stop until it is confirmed or the connection drops.

- **The SVGs of the button icons** (ADR: [Editor UI](adr/0013-editor-ui.md)): Biome checks `.svg` too, and the third-party icons have no `<title>`, so `app/src/renderer/controller/pad-icons` is excluded in `biome.json`. `parseIcon` understands only `<svg viewBox>` and `<path>`; a new file must first be prepared as `pad-icons/README.md` describes, or extra elements are dropped silently (`pad-icon.test.tsx` refuses such files). Only white and black fills become `currentColor`; for a new icon with other colors, decide in `paint` how to replace them.

### Where renderer files live
- **The order of stylesheets**: the build puts each stylesheet into `index.css` in the order it is first imported, and that order follows the imports as Biome sorts them, so moving files or changing import paths can change the cascade. That is why `App.tsx` starts by importing the components' stylesheets one by one in cascade order, with `theme.css`, `ui.css` and `shell.css` last. A new component stylesheet goes into that list; after moving files or changing imports, check that `out/renderer/assets/index-*.css` of `npm run build` is byte for byte the same as before.
- **Tests that scan the whole folder stay at the top of `src/renderer/`**: `forced-colors`, `theme-contrast` and `doc-names` scan from their own folder down; moved into a subfolder, they would scan only that subfolder, and a new `outline: none` or UI text elsewhere would no longer be checked, without any test failing. When moving a stylesheet, change the paths in those two tests' tables.
- **Places that read renderer files by path**: `padlabel_test.go` reads `controller/controller-model.ts`; Main's `overlay`, `pad-capture` and `system-settings` tests; the `activity-model` and `mapwizard` tests (which read daemon files, with `../` by folder depth). When the `import.meta.glob` of `pad-icon.tsx` matches nothing, it returns an empty object and the build does not fail; only `pad-icon.test.tsx` notices.

### The profile library and picking apps
- **The current profile in E2E**: an unbound app switches to the default profile, and during E2E the foreground is often a terminal. `fixture()` writes `lastProfile:"paint"` in `state.json` and `enabled:false` in `config.json` to turn off switching by app; after turning the switch on, use `profiles.activate` to get back to the profile needed.

### Importing scripts and external programs
- **Importing scripts and opening folders**: the renderer never gets a file system path. Confirming a replacement writes only what Main read the first time (a one-time token), shows no dialog again and accepts no path from the renderer; otherwise what was confirmed and what is written might not be the same file. Node's fs error messages carry absolute paths (with the user name), so every fs failure in Main is replaced by a fixed message; the daemon's unclassified error (-32098) likewise. The main.ts of a new script must not have bindings that take effect, or once a profile refers to it, the script would take over that button.

### E2E
- **The foreground limit**: the helper that records shortcuts looks at the system foreground, not Electron's focus. Windows' foreground lock sometimes keeps a test window that just started from getting the foreground, and `recordShortcut` fails after 10 s; this is the desktop's state: rerun it on its own, and never send keys to grab the foreground (invariant 6). While someone uses the computer, set `PADMATE_E2E_DISPLAY=secondary` to move the window to the first non-primary display.
- **E2E in a git worktree**: when the worktree's `app/node_modules` is a junction to the main repository, the path of electron.exe resolves to the junction's target, `ownwindow.TrustedPaths` refuses the registration, and the test waits until it times out. A worktree needs a real node_modules (`npm ci`, or a copy).

### Overlay
- **It must never take the foreground**: an activated overlay means padmate is in the foreground, and the daemon stops sending keys to the painting app (OUT-25). It is shown only through `showInactive()`, positioned only with `setBounds`, and `overlay.ts` and `overlay-window.ts` may contain no `show()`, `focus()`, `moveTop()` or `hide()` (`overlay.test.ts` reads the source to check).
- **Closing the window only hides it**: while connected to the daemon, the main window's `close` becomes `hide()` (`closeHides`). Any path that really means to exit must make one of `quitting`, `trayExiting` or `quitHeld` true before it calls `window.close()`; otherwise the window hides, the exit is canceled and the process stays in the background. While the overlay lives, it must also be destroyed in the main window's `closed` and `before-quit`.
