## SDL and controllers

### Basic behavior and hints
- **SDL hints**: before `SDL_Init`, `input.Open` sets `SDL_JOYSTICK_ALLOW_BACKGROUND_EVENTS=1`, `SDL_NO_SIGNAL_HANDLERS=1` (otherwise SDL takes Ctrl+C) and `SDL_JOYSTICK_HIDAPI_COMBINE_JOY_CONS=0`, then the preset and `--hint`. A hint of the same name in the environment wins. `SDL_Quit` resets the hints, so each Open sets them again.
- **SDL behavior**: SDL sends events only for open gamepads, so a gamepad is opened on GAMEPAD_ADDED. The first value of each axis is sent twice. For a virtual gamepad, `VirtualJoystickDesc.Version` is filled in by hand as 136, and `SDL_UpdateJoysticks` must be called after changing its state. On detach, SDL first lifts held buttons and centers the axes, then sends removed; padmate still has to ReleaseAll. Device ids are not reused within a process; a reconnect is recognized by DeviceKey. The release of the guide button is delayed to 250 ms after the press, and presses in between are dropped.

### Device info and identity
- **What DeviceKey rests on**: a virtual gamepad has an empty serial and path; its GUID is `ff00`, the CRC-16/ARC of the name, the first 9 bytes of the name, then `00 76 01`. Virtual gamepads of the same name can only be told apart by #N; for two whose names share their first 9 bytes, SDL reports the second under the first one's name, so tests make the first 9 bytes differ. XInput's path is the slot, and DeviceKey does not use it.

### Recovering from disconnects and lost events
- **Rescan on wake**: `Reenumerate(ctx)` publishes the full state as a `DeviceState` that cannot be dropped; wait for its internal fence to pass before `Supervisor.Sync`. The router treats the snapshot as a Resync, not as a new press. While a receiver is still dormant, it must not be brought back from cached state.

### 2.4 GHz receivers and the Switch protocol

- **2.4 GHz receivers**: over USB, the ConnectionState of a HIDAPI device is always WIRED, so it cannot tell that the controller turned off. A non-Bluetooth Switch controller that is silent for 100 ms only gets ForceUSB sent again; it is not disconnected, and the button state stays as it was before it turned off. Reports produce events only on changes, so neither the absence of events nor the absence of held controls proves that the controller is still there.
- Closing the gamepad puts a USB Switch device back into simple mode, after which it no longer reports properly: do not close it after a synthesized disconnect.
- The resend is a synchronous write on T-input; each `hid_write` waits up to 1 s and tries 5 times (not tested), so "T-input stalled" cannot always be taken for sleep: the watchdog's grace is given once per silent stretch. The heartbeat reads HID reports itself (`DeviceInfo.Path` goes to `SDL_hid_open_path`, called only on connect; `SDL_hid_read_timeout(…, 0)` does not wait): in the full report 0x30, bytes 3–11 are the buttons and sticks, and only when they are unchanged while the timer in byte 1 changes does it prove that the device keeps reporting.

### Feedback effects
- SDL's `Rumble` does not queue: a call simply overwrites the one before. The mixer of `internal/haptic` schedules step by step on T-input, and sends a stop effect on a new program, a lost link and exit. `SetFeedback` carries a target `DeviceID`; with several controllers, layer state must not be broadcast; only 0 broadcasts.
- **`--dry-run` drives physical controllers too**: layer switches and pause make a real controller rumble and light up. Tests use only fake sources (`fakeSource` and the like) or virtual gamepads; never send `SetFeedback` to `Device` 0 (a broadcast to every one) in a test that may open a real controller.
- **Effect channels** (read from the source, not on real hardware):
  - LED: `SDL_SetJoystickLED` returns success at once when the color has not changed and its 5 s window has not passed, and it records the color after calling the driver whether or not that worked; so after a failed write, the same color within the window counts as a repeat. The LED cool-down is 7 s (`LEDCooldown`).
  - Rumble: when the strength equals the current one, `SDL_RumbleJoystick` does not call the driver, so between adjacent "on" steps, and when preempting, `Rumble(0,0,0)` is sent first. A duration of 0 with a non-zero strength rumbles forever; each step is limited to 1–5000 ms. Switch HIDAPI merges rumble writes into one every 30 ms and does not support trigger rumble; XInput has Rumble only, with no trigger rumble, LED or player number. Calls must follow the capabilities.
  - **Player numbers** are one table for the whole SDL process: give B the number n, and A, which held n, is moved. So before cycling, ask the whole table with `Effector.PlayerIndexTaken(n)` and use only free numbers; a controller without player lights must not touch the numbers. Writing a number for a controller SDL has removed stores a dead instance id in the table that nobody clears; for removed ones use `Mixer.Forget` and do not call the `Effector`.

### Battery readings
Written from the source (except the receiver entry). In go-sdl3, `SDL_POWERSTATE_ERROR` is the `uint32` 4294967295; do not take it for -1. The battery is a `DevicePower` event; do not add it to `DeviceInfo` (which must stay comparable, and is the format of traces). `low` in the state means "the warning went out and has not re-armed", not "the battery is low"; a new episode is recognized by the `episode` number.

- **A controller behind a 2.4 GHz receiver may always report a full battery**: CHARGING 100 % in Xbox mode, CHARGED 100 % in Switch/PS4 mode. The low-battery warning never goes off.

### Mappings, remapping and raw sticks
- Tested: `SDL_AddGamepadMapping` does not tell whether it added or updated; read it back with `SDL_GetGamepadMappingForID` and compare (ignoring `platform` and `crc`). When the environment variable `SDL_GAMECONTROLLERCONFIG` has a mapping for the same GUID, Add still succeeds but reads back the environment's mapping, so `MappingStatus.Applied` relies on the read-back.
- Tested: `SDL_ReloadGamepadMappings` drops every run-time mapping and also reads the file that `SDL_GAMECONTROLLERCONFIG_FILE` names: first rewrite the file to what should stay, then Reload. Controllers that stay get `REMOVED` plus `REMAPPED` (no `ADDED`), so events cannot be handled by name: first check whether `SDL_GetJoysticks` still lists it, then `SDL_IsGamepad`, or the controller is lost. A controller whose mapping did not change gets REMAPPED too: when the mapping text is the same, no `DeviceRemapped` is sent, or a modifier held on another controller would be reset and released.
- Tested: SDL sends no releases when it remaps, so a remap must be treated as a reset (`DeviceRemapped`, the router sends `Edge{Reset: true}`); otherwise Space stays held.

## Keyboard output and layouts

### Keyboard injection
- **SendInput**: on amd64 an `INPUT` is 40 bytes. Use `KEYEVENTF_SCANCODE`, and add `EXTENDEDKEY` for keys with the E0 prefix. F13–F21 are scan codes 0x64–0x6C, F22 0x6D, F23 0x6E, F24 0x76. `KEYEVENTF_UNICODE` is for text only.
- **The dwExtraInfo tag**: injected events carry `"padm"<<32 | nonce` (`output.ExtraInfo`). The keyboard LL hook receives the full 64 bits, and tests rely on it to swallow only the events with their own nonce.
- **Special keys** (tested): Pause is sent as VK_PAUSE (wScan 0x45); the numpad 0x47–0x53 is translated by NumLock, so Num0–9 and NumDecimal are sent by VK; for the navigation keys, PrintScreen and Pause, `MapVirtualKeyEx` returns scan codes that differ from the physical keys', so they cannot be derived from it.
- **Menu masking** (tested): before a lone Alt or Win goes up, MenuMask inserts a press and release of vk 0xE8 in the same batch. The mask key enters neither the Arbiter nor the ledger; `padmatectl send` and injecttest do not go through MenuMask.
- **UIPI**: injecting into a window of a higher integrity level fails silently; it is only detected and reported, never bypassed. Win+L and Ctrl+Alt+Del cannot be injected.

### The held-keys log
- The log is written before each SendInput with a new press. "A temporary file + MoveFileEx" takes up to 7.5 ms, so the log is rewritten in place on an open handle: `heldfile_windows.go` calls CreateFile itself (without `FILE_FLAG_OVERLAPPED`) and uses `windows.WriteFile` with an OVERLAPPED offset; the OVERLAPPED, the count and the buffer live in a struct on the heap, since local variables would escape and allocate (`TestHeldLogNoAllocs`).
- A test's heldFile must be in TempDir, never `%LOCALAPPDATA%\padmate\run\held.bin`, and the test must also set KeyDown (`liveConfig.keyDown`, `LoopOptions.KeyDown`), or the sweep reads the machine's real keyboard state.
- **The identity in the log's header**: `GetAsyncKeyState` cannot tell injected from physical presses, and a log left by another boot or sign-in session would release keys the user is holding now, so only a log of the same identity is swept. The identity is the LUID plus the sign-in time (`LsaGetLogonSessionData`), compared bit for bit; do not use "now minus `GetTickCount64`" (the clock jumps and drifts after sleep). A test's log must carry the same identity as the Loop (`output.EncodeHeld`).

### Rules for tests with real injection
- **LL hook timeout** (by Microsoft's documentation, not tested): when the hook procedure times out (LowLevelHooksTimeout, at most 1 s), that key is not swallowed, and the hook may be removed silently, after which every injected key reaches the foreground program. So fence every batch and stop injecting on failure: use `InjectFenced` (`InjectFencedMixed` with mouse events), and the O(1) `WaitOwn` for many batches (ARCHITECTURE §14).
- A swallowed CapsLock, NumLock or ScrollLock still flips the system's lock state; tests press them in pairs.
- **A mouse button press can never be injected alone**: if the hook does not swallow it, it is a button held on the screen. Put the press and the release in the same batch (`InjectFencedMixed`), with the canary at the end of the batch; an unpaired batch is refused before anything is sent. `InjectFenced` refuses batches with mouse events.

### The mouse
Tested on Windows 11 x64.

- **Buttons can be held**: every exit path must lift them; the held-keys log uses the slots of VK 0x01, 0x02, 0x04, 0x05 and 0x06. Pressing a button again while it is down makes the app see half a double click, so the Arbiter never presses twice, and profiles refuse hold together with typematic repeat. `GetAsyncKeyState` cannot tell an injected mouse button from one held physically, so the sweep may inject a release for a left button the user is holding.
- The mouse LL hook (`EnableMouse`) calls its procedure for every movement: it first asks `MouseOptions.Watch`, and events it does not care about go straight to `CallNextHookEx` (not copied, not queued, not swallowed); otherwise the physical mouse would lag. It is installed on the keyboard hook's thread; unhooking removes the mouse hook first, then the keyboard. In the hook, `dwExtraInfo` keeps only its low 32 bits, so `output.IsPadmate` is always false for mouse events; compare the low 32-bit nonce instead (`Recorder.mouseOwned`).

### Pointer movement
- `dx` and `dy` are amounts of movement, not pixels: the system scales them by "pointer speed", and with "Enhance pointer precision" on they also go through the acceleration curve (tested: +300 → +600). padmate does not change these settings; the unit of `mouseSpeed` is SendInput's movement. A movement with both `dx` and `dy` 0 never reaches the hook, and the engine does not send one.

### Media keys and typing text
- Media keys are sent by VK, with the E0 scan code in `wScan` and `EXTENDEDKEY`, without `SCANCODE` (`KeyEventFor` gives `ByVK`); they are ordinary keys that can be held. If a test does not swallow one, the volume or the playback state changes; while recording a shortcut, the capture hook does not swallow physical keys, so recording a volume key changes the volume.
- A Unicode event's press and release go in the same Send, and enter neither the Arbiter's key table, the held-keys log nor the startup sweep. When a send partly fails, the release is sent again at once; if that fails too, it goes to `Arbiter.stuck`, which `ReleaseOwners` sends and `Held()` counts (invariant 1).
- Tests must never inject a Unicode press without `UnicodeCanary` (one that gets through is a character typed into the foreground window): first inject the release of U+FFFF, and only once the hook has swallowed it, the press.

## Win32 and message loops

- **Win32 bindings**: generated with mkwinsyscall; never write `NewLazySystemDLL`/`NewProc` by hand. Each package writes `//sys` lines in `syscall_windows.go`, and `task gen` generates `zsyscall_windows.go`. The generated functions return `EINVAL` when the last error is 0, so judge failure by the return value. DLLs and functions are loaded on the first call (which allocates), so call outside a hook callback, once, what the callback will call (`winhook.Start` calls `latency.Now` first).
- When the last GUI thread of a process exits, Windows destroys every window class, after which CreateWindowExW fails with "Cannot find window class"; so winsession registers its window class on T-session on every Start.
- **padmate's own windows are a foreground too**: while the tray menu or the Electron UI is open, it is the foreground, and without filtering the profile would switch to the default one. padmated filters by its own PID; a registered UI keeps the current profile and releases nothing, and `app.foreground` is published as usual with `own:true`. Tests call `onForeground` with a fake `winfocus.App` and never change the real foreground.
- **The tray**: `fyne.io/systray` must run on the main thread.
  - "Open window" starts `padmate.exe` only in the installed build: a development or test build that started it would open the app with real data and `--inject`. Double clicks are counted by `tray.Taps`; do not block in Tap. The cleanup worker must not call systray's Quit (onExit is nil before Register); it only posts WM_QUIT to the main message queue. Failures, panics and unexpected returns from the loop must keep a non-zero exit code.
- **The real foreground changes a test's profile**: a library-mode test with the real winsession/winfocus picks a profile by the real foreground about 50 ms after starting, and an unbound foreground replaces `--profile-id` with `default`. Such tests write `{"schemaVersion":0,"enabled":false}` in the data folder; tests of selection use the fake foreground of `startSelectionLive`.
- **The security descriptor of a named event**: `CreateEvent(nil, …)` uses the default DACL of the creator's token. By the UAC documentation (not tested), the default DACL of an elevated token grants only Administrators and SYSTEM, so a non-elevated process of the same user cannot open it with `EVENT_MODIFY_STATE`. So `emergency.Listen` sets `D:(A;;0x1f0003;;;<user SID>)S:(ML;;NW;;;ME)` explicitly (`TestListenSecurity`). When the event already exists, `CreateEvent` returns a valid handle together with the error ERROR_ALREADY_EXISTS; check the handle first, or it leaks.

## Pause, system events and exit

Tests of what happens while the screen is locked, during sleep or sign-out use only fakes, virtual gamepads and `internal/winsessiontest`; they must never really lock, sleep or sign out the machine. `winsessiontest` refuses `HWND_BROADCAST`, other processes and windows of other classes.

### Suspend and resume
- **Synthesized releases and late holds during a suspend**: while the screen is locked or the machine sleeps, SDL may first send a synthesized up, and the down of the original hold arrives late, after unlocking. The router quarantines buttons and axes active before and during the suspend, each on its own: an up or a return to center during the suspend, and an empty `DeviceState`, do not lift it; after resuming it must see active → release/neutral once more, and time cannot lift it. Axes first moved during the suspend, and controllers that connected while suspended, are quarantined too, so after resuming a stick has to return to center and be pushed again before it maps; this is by design. A known gap: for a button pressed only during the suspend, with no event at the time, a late down cannot be told from a new press after resuming. The model of FuzzRouter must judge neutrality by the same rules (`frNeutral`, `axisApplies`); change it together with the analog settings. `Supervisor.Suspend` is not in the event order, so the fuzz's `frSuspend` first sends a `removed(0)` of an unknown controller to make sure the previous event has been routed.

### Pause and the emergency combo
- **Where it is detected, and on which thread**: `input.ComboWatch` sees an event on T-input before it goes into the channel (so it also sees events a full channel drops); do not move it behind the channel. `OnCombo` runs on T-input and may only call `output.Loop.Block`, never `Do` (which waits for T-output). `ComboHeld` is not written to traces; golden tests and `--fake-input` insert it with `input.ExpandCombos`.
- **Pause edges** are delivered through `Edge.Pause`, and every edge during pause carries PauseOn. Only starting new slots paused is not enough: a press queued before a restart would be replayed after resuming (`TestPauseRestart`).
- **Changing the emergency combo, and lock order**: when config.json's `safety` changes, call `ComboWatch.Repick` on T-input only through `Source.RepickCombos`; do not touch ComboWatch from another goroutine, and do not reopen the Source to change combos. In `commitConfigLocked`, take `configApplyMu` before `profileMu`; the other way round deadlocks.

### Exit
- **Sign-out, shutdown and SIGTERM** (by the documentation, not tested): the GUI-subsystem release build receives no console events; padmated learns of them from `WM_QUERYENDSESSION`/`WM_ENDSESSION` in the winsession window. About 5 s after `WM_ENDSESSION` returns, the system ends the process, so it waits at most 3 s. When T-session called `OnStop("session-end")` (`liveRun.sessionEnding`), the shutdown log is written before T-session closes; otherwise T-session closes first, so the final log lines are not lost. taskkill without /F sends WM_CLOSE, which is handled as a stop; with /F there is no chance, and the release relies on the held-keys log.
- **The limit on input cleanup after the release**: after the supervisor's Run and `Loop.Stop` have finished releasing and retrying, the feedback/input tail shares a limit of 1 s; never wrap a timeout around the key release. On timeout, call the non-blocking `Source.RequestClose` (`SetFeedback` may wait for a stuck T-input). A timeout, or a panic/Goexit of the cleanup worker, logs an error and returns 1, and the final log is still written and the session window closed; a late cleanup must never reopen output.
- **Waiting on tray exit**: close the `output.BlockExit` gate first, then wait (2 s) for the UI to finish saving; presses during that time send no keys, and the gate has no way to reopen. IPC keeps serving, and `profiles.put` and `config.put` still write to disk. `ui.exitReady` is matched to the session that `Hub.PublishSync` returns; do not use a name the client reports.
- **The installer needs the daemon to exit**:
  - `Endpoint.Close` deletes `daemon.json` as soon as the daemon starts stopping, so `padmatectl quit` opens the process by pid before it sends the request. The pid may be stale or reused, so quit checks that the image name is `padmated.exe`; the installer passes `--under <installation folder>`, and a process whose image path is outside it is neither asked nor waited for (`daemon.json` may belong to a development build or a portable copy). `padmatectl ui-bridge` (a child process of the UI) holds `padmatectl.exe`, so a reinstall or an uninstall must make the UI exit first (`daemon.exiting`).
  - `release-all` cannot replace quit: it makes every `--inject` padmated of the user (including ones installed elsewhere) release its keys and destroy its scripts. Use it only when quit fails, and never under the `PADMATE_INSTALLER_TEST_ROOT` override. If after 10 seconds a `padmated.exe` is still in the installation folder and `release-all` has not run, run it once before ending the process, because `TerminateProcess` does not release held keys, and a full uninstall deletes `held.bin` as well.

## Engine, slot and supervisor

- **runtime.Goexit**: while Goexit unwinds, `recover()` in a defer returns nil, so a flag is needed to tell it from a normal return. `output.Loop` and `slot.RunLoop` both do this and still release the keys after Goexit; the supervisor treats a Goexit of the slot loop as a panic and restarts the slot.

### Scripts with the slot and the supervisor
- **The edge barrier of the first setup**: for a profile with a script, the supervisor sends a Resync on every assign, and the candidate starts only once the slot has finished the Resync; otherwise the worker may read `pad.isDown` from the old all-released state. When a hot reload adds a script, the slot must open the first-start gate with the snapshot it has.
- **Persistent layers and release**: exit, profile switches and disconnects must save the selection before canceling controls, or CancelAll clears the toggles and an empty state is written back. LayerMemory does no disk I/O; leaving the loop calls `preserveLayers` first, and the flush comes after the keys are released. Restoring does not include hold/latch.
- **Scripts consuming one edge**: the slot must not send ButtonDown/Up separately by what was consumed; consuming only the release leaves a declarative hold behind. Scripts are resolved at the state transition of the engine's `stepButton`, and physical and virtual controls take the same path. A script's `pad` may only use the snapshot the slot loop copied.

### The Arbiter's timing and the event-gap queue
When `SetEventGap` is above 0, the Arbiter queues the key events of a command and sends them a gap apart. Go through this list before changing the Arbiter in `internal/output`; each item has a regression test or fuzz corpus.

1. **Failed releases and forced release**: after a release and its retries fail, refs is 0 but the physical key may still be down; while the key is still in the ledger, a queued tap of the same key must wait. A queued press that was displaced may already be down, so its release is sent as usual (`mayBeDown`). Releasing only modifiers triggers an input-method switch, so the mask key is inserted before the first modifier goes up.
2. **Shared presses are counted per owner**: a press not yet sent may be borrowed by another owner, so keyState records `users` and drops the key only when all have released; otherwise someone else's Ctrl+X becomes X. The queue cannot grow without bound: Repeat and taps on a held key queue at most one extra press per key, and Downs alternating faster than the gap merge into the last one (`mergeDown`, `MergedKeys` in the fuzz). Releases enter the queue in their order without gap (`zeroDeadline`); queuing them only after the press goes out would hold two combinations at once.
3. **A canceled tap must not leave a hold**: a tap's hold first goes into `ref.minPress` and joins `minHold` only when it ends normally; otherwise, after a forced release cancels the tap, a key held by another Down stays held past its Up, and Ctrl+Num1 becomes Ctrl+Alt+Num1 (`TestEventGapCanceledTapHold`). Timing comes only from the profile, not from `PADMATE_BENCH`; `slot.Advance` runs the Arbiter first, then the script, then the engine.

### Gestures and buffering
- **Gestures that fire on release cannot hold**: `commitMulti` runs the action on a copy of `e.multi[c]` and then drops the copy, so a `Down` combination, repeat or held layer would have nobody to end it (invariant 1). So release, tap and multi-taps can only use tap mode, cannot have repeat, and their layer actions cannot be hold; `profile.Parse` and `engine.Compile` both check this (`TestParseAndCompileAgree`). A new gesture either runs on `e.ctl[c]` or adds the rule in both places. Bindings returned by a Level of `Options.Registry` do not go through Compile; check them with `engine.CheckBinding` first.
- **Edges in the buffer cannot be overtaken**: while the buffer is not empty, new edges (including releases of controls already dispatched) go to the end and are replayed in their order. Overtaking an edge of the same control leaves a key stuck; overtaking another control's reorders them (a modifier released first loses the combination, a multi-tap window is committed early). A Pending control's own release cannot overtake either: when the drain decides on a tap, only the tap action runs (`decideTap`), and the release stays in its place.

### Analog controls and sticks
- **Ask the engine for stick settings, not the Program**: calibration lives in `Engine`; read it with `Engine.Analog()`. A calibration change must not CancelAll (dragging a slider would release keys); it goes through `settleVirtual(now, false, false)`, and `Reset` does not clear the calibration. `configNeedsRestart` compares only the ignored devices; otherwise every slider drag would ask for a restart.
- **Sticks in mouse mode**: after `CancelAll`, a stick still pushed has to return to the dead zone before it moves again (`mouseLock`); `Reload` and calibration changes do not lock it, or the UI's autosave would stop the pointer. An `inputOnly` engine has no `Output`, so it cannot call `Output.Move`/`Jump` or schedule deadlines.

### The function key
- The edges of the function key (`Program.fnKey`, one of `back`, `start` and `guide`) return in `stepButton` before `inputOnly`, `Options.Button` and the buffer, so `e.ctl[…]` is never pressed for it. `st.down = e.physical[c]` in `cancelAll` must leave it out; a `Reload` that changes the function key must clear the new function key's former `e.ctl[…]` and `fnActive`. A buffered edge carries the function key in effect when it arrived (`Input.fn`); do not read `e.fnActive` in `press`.

### Sequences, decisions and fuzzing
- Canceling a sequence marks the sequence before canceling taps and text (`cancelQueued`: `endSeq` first); otherwise one more step goes out. `TapSequence` (an array of KeySpecs) does not queue and runs in parallel with other owners, which golden outputs depend on; `Sequence` waits for the earlier ones to end, and `engineOutput.TypeText` must go through `Sequence`. A wait in a sequence counts from the physical release of the step before, and does not add the `gap`.

- **A remap does not clear a pending quarantine**: `router.remapped` clears only `d.state` and `hasSnapshot`, not `d.recovery`. A change that cleared `d.recovery` passed the unit tests, the golden files and the corpus alike; the last four seeds of `frSeeds`, which cross a remap, each kill one such change, and they must keep passing.

## Latency and timing

The design of end-to-end latency is in [ADR: Engine and threads](adr/0005-engine-and-threads.md).

- **Windows timing**: `time.Now` jumps only every 0.5–2 ms; for microseconds use QPC (`latency.Now`). Go's `time.Sleep(1ms)` actually takes about 1.05–1.6 ms; Win32's `SleepEx(1)` usually about 15 ms. A test that requires "an interval measured with QPC is at least some wait" cannot use `time.Sleep`; spin on `latency.Now` instead.
- **SDL clock**: `SDL_GetTicksNS = (QPC − tick_start)·1e9/freq`, so `Event.Time` can be converted back to QPC: `Source.SampleTicks` takes readings, and `latency.CalibrateSDL` finds tick_start. Tested: SDL's counter frequency equals QPC's (10 MHz).

## Scripts

The decisions are in [ADR: Scripting runtime](adr/0010-scripting-runtime.md).

### goja, esbuild and types
- **goja**: supports ES2015+ and async/await, but not ESM, top-level await, async generators or for-await, so esbuild bundles to an IIFE. A Runtime can be used by one goroutine at a time. The feature table is `internal/script/compile/goja_features.json`.
  - `Runtime.Interrupt` has no effect inside a native Go function, so host APIs must return quickly. An Interrupt sent while no call runs makes the next call fail at once, so every call ends with `ClearInterrupt`.
  - `Object.Get` returns Go's nil for a missing property: an array with holes gives nil at an index, and calling `.Export()`/`.String()` on it panics and restarts the whole slot. Check for nil before reading the elements of an array a script passes (`stringValue` in `hud.go`).
- **esbuild**: `TsconfigRaw` must be set, or it reads a tsconfig.json outside the root. A computed `import()`/`require()` path is expanded as a glob without going through OnResolve, so OnLoad has to check again.
- When the `padmate` module gains a value member (like `hud`), `padmateStub` in `compile/plugin.go` must export it too; otherwise `import { hud } from "padmate"` fails to bundle, while tests that only exercise the runtime still pass.
- **The script API version is kept in four places**: `dtsgen.SupportedAPIs` (the current version first; `HostAPI` is the first entry), the `script.api` enum of `schema/profile.schema.json`, `apiVersion` in `internal/script/host.go`, and `@since`/`@until` in the d.ts. Tests align the first three; after changing the schema's source, run `task gen` for the copy. A new value member of the d.ts must go into `StableMembers` or `PreviewMembers`, and members macros can use (`@macro`) must be stable. When a new version changes a member of the previous version, it needs a shim and a consistency test. After raising the version, fixed profiles that were not raised get one more `/script/api` warning, which breaks "zero diagnostics" assertions (find them with `grep -rE '"api": ?"0\.N"'`).

### Macros
- **Output scope**: a normal end cannot use `ReleaseOwner` (it would cut short a last tap that was not awaited, and release keys of other owners); it lifts with `Up` one by one. Only the 60-second limit and the safety boundaries use `ReleaseOwner`.

### The watchdog
- **QueryThreadCycleTime** counts TSC time; sleep does not count, and migration causes no jumps. At startup it is calibrated against QPC (10 busy waits of 1 ms per group); the loop must not call `runtime.Gosched()`, which lowers cycles/µs and makes 900 ms of script CPU time look like more than 1 s. `GetThreadTimes` has a granularity of 15.6 ms and is not used.

### Lifecycle, pause and profile switches
- **Pause cannot just ReleaseKeys**: `every`, `sleep` and Promise continuations would still press keys again through `RunDue`. Pause must invalidate the old Host and refuse candidate swaps, and resuming rebuilds on the worker; an initial pause must take effect before the factory builds, or `onActivate` has already produced output.
- **Owners, teardown and invalidation**: the cycle is shared by the whole scriptRuntime, so a new `Lifecycle` must not start numbering again from Cycle 1; otherwise `Dispose.ReleaseOwner` of a canceled old candidate would release new keys of the same slot and gen. The slot loop releases the old Host's owner first, then disconnects the output sink, and only then lets the worker run the teardown. When the first Send of an offline emergency release fails, the supervisor still completes the ReleaseAll barrier of every slot before reporting the combined error; otherwise an old every/sleep presses keys again once the gate reopens.
- **Profile selection and hot reload**: changing the profile key must stop the old lifecycle before the engine is replaced and layers are restored, and must not take the hot-reload path that keeps the old script; otherwise, when the new script's setup fails, the old profile's every keeps sending to the new foreground. The old teardown also must not write the old layer selection into the layer memory of the new ID (`TestProfileSwitchDisposesOldScriptWhenNewSetupFails`).
- **Effects are canceled by (class, controller), regardless of which runtime started them**: while an old and a new runtime both exist (`Lifecycle.Swap`, `pollReload`), an old cancellation that arrives after the new `onActivate` started its effects would end them too, so both places call the old Host's `CancelEffects()` before the new activation.

### Output
- **Tap completion crosses threads**: the callbacks of `output.Loop` run on T-output and may only post to a queue and wake the slot; they cannot call goja or `Host.RunDue`, or call the Loop again. Pause, unloading and destroying disconnect output first and abandon the old Promises; `Host.Dispose` must abandon old tap Promises before the teardown.

## UI

The design is in ARCHITECTURE §12, the decisions in [ADR: Editor UI](adr/0013-editor-ui.md) and [ADR: Overlay](adr/0014-overlay.md).

### Processes and security
- **Development isolation**: `task app:dev` uses a private daemon in `.cache/ui-bin` and data in `.cache/ui-*`; isolating only the data folder while still connecting to the user's discovery folder, pipe or mutex is not enough. The daemon must be in a layout that `ownwindow.TrustedPaths` accepts, or `ui.register` is refused. When an exe is in use, check its path before closing the matching instance; never kill by process name.
- **The Electron security bridge**: the renderer has no Node and no discovery token. Main connects to the pipe through `padmatectl ui-bridge`, and shows the window only after the first UI registration succeeds; registration cannot be skipped, and not every electron.exe counts as this program.
- `webContents.send` has no back-pressure, so Main limits the batches in flight and the preload acknowledges what it consumed; when navigation starts, sending pauses and old batches are reclaimed, resuming only after `did-finish-load`. New IPC topics are added on both sides together (`ipc-wiring.test.ts`). The report on the startup failure page is written by another program, so Main keeps only the fields it knows; for configuration backups, Main takes only the name the renderer gives, checks it with `validateConfigBackup` and builds the path itself.
- **Output to our own windows**: the protection must come before T-output's commands and timers; hiding output only in the page cannot stop SendInput. The transition gate opens only after the slot/script cleanup succeeds, and checking the transition generation and opening the gate happen within the same command on the output thread; a failed release keeps the gate shut, and a transition never re-sends keys that are held.

### The editor: saving and drafts
- **Saving with the single-set UI**: the UI edits only `layers.base`, but the draft must be the whole profile, never rebuilt from the UI's model, or the other layers, common, layer actions, block, defaultLayer and the feedback settings would be lost. When defaultLayer is not base, the whole profile is read-only.
- Changes save at once: a text field commits only on Enter or on leaving it (`useCommitField`), so tests must `blur` or press Enter after `change`. Changing the action type first gives a draft with empty parts, and what is saved is the `savedForm` without them. A reread caused by `profile.changed` may come after our own save; if the revision changed, read again.
- **The daemon rewrites profile.json**: renaming, deleting and removing legacy scripts change the file directly in the daemon. Before the call, `flush()` waits for the write, and the call is not made if it cannot save; after it, `reload()` rereads the draft, and `clearHistory(id)` runs only when the `profiles[].id` returned include it. Changing only the revision would make the next autosave write the old name back; not clearing the undo history when it should be means Ctrl+Z changes the old name back.
- **Inherited content is for display only; writing back goes through `writeBack`**: `draft` is always the profile's own file; `withInherited(draft, parent)` adds the parent's content, for the controller picture, the button list, the sheet and the drawer to read only. Before giving a merged `Profile` to `state.edit`, call `writeBack(draft, parent, next)`, or one small edit copies the parent into the child. Everything that reads "the saved form" must pass `parent` to `savedForm`.

### The editor: buttons, the function key and sticks
- **A stick's two selection ids**: `leftstick` and `rightstick` are "rotation", `leftstick.press` and `rightstick.press` are "press", while the binding key `leftstick` is the binding of pressing the stick. A binding key finds its drawer through `calloutFor`, a selection id finds its binding through `bindingKey`, and comparing "is this callout the one selected" goes through `calloutOf` first; otherwise the "press" cell has no name and lights no leader line.
- **The function key's set**: when the function key's set is edited, `swapView` swaps it into the place of `layers.base`, so all code that "looks through every set of buttons" must count `functionSet` in. Which button is the function key is decided by `functionKey` in config.json; the pure functions all take it as a parameter without a default, so never judge it by the control names `back` or `start`.
- **The mapping wizard's capture and cleanup**: the wizard opens a capture that stays: window `blur`, locking the screen and sleep call `windowAway()` and do not stop it; closing, reloading, a renderer crash and exit call `stop()`; a disconnect calls `disconnected()`. Do not turn blur into `stop()` (switching to another program while the wizard is open would make the controller's buttons send shortcuts), and do not turn other paths into `windowAway()` (the window would be closed while mapping stays stopped).
- **Shortcut capture**: start/stop/events all carry a session, and a start arriving late on unmount may only stop its own session; the hook only observes, and automated tests must never really press Win+L or Ctrl+Alt+Del or sign out. When recording the emergency combo, a `capture.start` that timed out or failed may still reach the daemon, and a `capture.stop` may not have gone out, so once `pad-capture.ts` has sent a start, it keeps sending stop until it is confirmed or the connection drops.

- **The SVGs of the button icons** (ADR: [Editor UI](adr/0013-editor-ui.md)): Biome checks `.svg` too, and the third-party icons have no `<title>`, so `app/src/renderer/controller/pad-icons` is excluded in `biome.json`. `parseIcon` understands only `<svg viewBox>` and `<path>`; a new file must first be prepared as `pad-icons/README.md` describes, or extra elements are dropped silently (`pad-icon.test.tsx` refuses such files). Only white and black fills become `currentColor`; for a new icon with other colors, decide in `paint` how to replace them.

### Where renderer files live
- **The order of stylesheets**: the build puts each stylesheet into `index.css` in the order it is first imported, and that order follows the imports as Biome sorts them, so moving files or changing import paths can change the cascade. That is why `App.tsx` starts by importing the components' stylesheets one by one in cascade order, with `theme.css`, `ui.css` and `shell.css` last. A new component stylesheet goes into that list; after moving files or changing imports, check that `out/renderer/assets/index-*.css` of `npm run build` is byte for byte the same as before.
- **Tests that scan the whole folder stay at the top of `src/renderer/`**: `forced-colors`, `theme-contrast` and `doc-names` scan from their own folder down; moved into a subfolder, they would scan only that subfolder, and a new `outline: none` or UI text elsewhere would no longer be checked, without any test failing. When moving a stylesheet, change the paths in those two tests' tables.
- **Places that read renderer files by path**: `padlabel_test.go` reads `controller/controller-model.ts`; Main's `overlay`, `pad-capture` and `system-settings` tests; the `activity-model` and `mapwizard` tests (which read daemon files, with `../` by folder depth). When the `import.meta.glob` of `pad-icon.tsx` matches nothing, it returns an empty object and the build does not fail; only `pad-icon.test.tsx` notices.

### The profile library and picking apps
- **The current profile in E2E**: an unbound app switches to the default profile, and during E2E the foreground is often a terminal. `fixture()` writes `lastProfile:"paint"` in `state.json` and `enabled:false` in `config.json` to turn off switching by app; after turning the switch on, use `profiles.activate` to get back to the profile needed.

### E2E
- **The foreground limit**: the helper that records shortcuts looks at the system foreground, not Electron's focus. Windows' foreground lock sometimes keeps a test window that just started from getting the foreground, and `recordShortcut` fails after 10 s; this is the desktop's state: rerun it on its own, and never send keys to grab the foreground (invariant 6). While someone uses the computer, set `PADMATE_E2E_DISPLAY=secondary` to move the window to the first non-primary display.
