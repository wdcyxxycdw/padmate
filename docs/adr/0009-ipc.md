# ADR-0009: IPC: JSON-RPC over a named pipe

[中文](0009-ipc.zh-CN.md)

Related: [ARCHITECTURE §11](../ARCHITECTURE.md#11-ipc)

## Context

Both `padmatectl` and the Electron UI control the daemon over IPC. Whoever can write a profile can make the daemon send any key to the foreground, so IPC is open to the signed-in user only. It must also be easy to implement in Go and in Node, support subscriptions with push, keep slow clients from slowing the engine, and not hand the token to another process of the same user that creates a pipe of the same name first.

## Decision

1. **The named pipe `\\.\pipe\padmate-<SID>`** (go-winio on the Go side). The DACL first denies network sign-ins and then allows the current user; the order cannot be reversed. Remote clients are refused. The first instance creates the pipe with `FILE_CREATE`; if a pipe of that name exists, the daemon exits.
2. **The discovery file `%LOCALAPPDATA%\padmate\run\daemon.json`** holds the pipe name, the pid, the protocol version and the token. Only the current user can access it, and the token is new on every start.
3. **The client checks the server before it sends the token.** It checks that the PID of the pipe's server equals the pid in the discovery file, and disconnects otherwise; the server receives zero bytes. Node's pipe API cannot do this, so the UI connects through `padmatectl ui-bridge`.
4. **JSON-RPC 2.0 over NDJSON.** Events are pushed with `subscribe` plus notifications; a topic's name is the notification's method. The first message must be `hello{token, protocol, client}`, checked before the RPC service starts; a wrong first message, a wrong token, a wrong protocol or an oversized message disconnects at once.
5. **Bounded connections.** Frames, batches, the number of clients and the handshake time all have limits. A batch has no guaranteed order; a client should wait for the response to a write before it queries.
6. **Back-pressure: the engine never blocks.** Publishing does no network or disk I/O. Each connection has a bounded event queue; when it is full, events are dropped and `dropped{n}` is sent once it recovers. A separate worker sends, and a write that times out disconnects. `daemon.exiting` is published synchronously and waits up to 250 ms.
7. **`protocol` is an integer**, raised by one for a breaking change; it is independent of `schemaVersion` and `script.api`.
8. **A way out beside IPC:** `padmatectl release-all` does not use IPC ([ADR: No stuck keys](0006-no-stuck-keys.md)).

## Costs

- The transport can be tested on Windows only.
- Busy topics rely on bounded queues and dropping, and the UI has to handle `dropped`.
- Other processes of the same user can read daemon.json and connect. This is within the design: processes of the same user can call SendInput anyway.
- daemon.json may be left behind after the daemon crashes, so clients must handle "the file exists but nothing answers".

## Alternatives given up

- **TCP on localhost, or WebSocket.** Processes of any user on the machine, and web pages in a browser, could connect; only the token would protect it, with no access control by the operating system.
- **gRPC.** It brings protobuf and a second code generator, while a JSON Schema → Go/TS generator already exists.
- **WM_COPYDATA or COM.** Hard to use from Electron.
- **The client does not check the server.** A process of the same user that creates the pipe first would receive the token and could pose as the daemon.
